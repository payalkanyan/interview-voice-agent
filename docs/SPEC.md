# Spec: voice mock interview coach

## What it is

A voice agent that runs a short mock interview. The user talks to it in the browser. It asks 4 fixed questions in order, reacts to each answer, and closes with short spoken feedback.

The goal is not a feature-rich agent. The goal is one that feels natural to talk to and is honestly measured.

## The conversation

1. The coach greets the user in one or two sentences and asks question 1.
2. It asks these questions, in this order, word for word:
   1. Tell me about a project you're proud of.
   2. What was the hardest technical problem in it?
   3. How did you know it was working well?
   4. What would you do differently now?
3. After each answer, it does exactly one of:
   - **Follow up** (once at most per question) when the answer is vague or skips the interesting part. The follow-up must reference something the user actually said.
   - **Nudge** when the user is stuck or didn't answer ("Take your time. Even a small project works.").
   - **Move on** with a brief acknowledgement when the answer is good enough.
4. After question 4, it gives 2 to 3 sentences of spoken feedback: one strength and one thing to improve, each tied to something specific the user said.
5. It says goodbye and stops.

## Persona

A calm, friendly senior engineer. Encouraging but honest. Short sentences. Never lectures.

## Hard rules

- Pipecat, Python 3.11+ (using 3.12).
- Cascaded pipeline: separate STT, then LLM, then TTS. No speech-to-speech or realtime audio models.
- Runs locally. Browser transport.
- One command to start: `make run`.

## Pipeline

```
browser mic
  -> SmallWebRTC transport
  -> STT: Deepgram nova-3 (streaming, with keyterms)
  -> turn detection: Silero VAD + Smart Turn v3
  -> LLM: Gemini 3.1 Flash-Lite (streaming)
  -> TTS: Cartesia sonic-3 (websocket)
  -> browser speaker
```

Interview state (which question, whether the follow-up is used) is held in code with Pipecat Flows, not only in the prompt, so question order is guaranteed.

Feedback is generated by a stronger model in a separate call, with a short bridging line spoken while it runs.

## Turn-taking and interruptions

- Do not reply during a mid-answer pause like "I worked on... um... a payments service".
- Do not leave dead air after the user clearly finishes.
- If the user talks over the coach, the coach stops within a few hundred ms and responds to what they said, then returns to the current question.
- A cough or "mm hmm" should not count as an interruption (require at least 2 words).

Every value I tune goes in the README with the default, my value, and why.

## Latency logging

Write `latency.jsonl`, one line per user turn:

```
{"turn": 1, "user_stopped_ms": ..., "stt_final_ms": ..., "llm_first_token_ms": ..., "tts_first_audio_ms": ..., "interrupted": false}
```

- All `_ms` values are milliseconds from session start.
- `user_stopped_ms` is when the user actually went quiet, not when end of turn fired.
- `tts_first_audio_ms` is when audio starts playing. If I can only capture server send time, I say so and estimate the gap.
- Logging is done by an observer, so it adds no latency to the pipeline.
- Also log `turn_end_ms` (when end of turn was decided) so the turn detection wait and the LLM wait can be separated.

A report script prints p50 and p95 of user stopped to first audio, and the average time in each stage.

## Transcript

`transcript.txt` and `transcript.json` for every session: who said what, in order, with session timestamps. Interrupted coach lines end in `[INTERRUPTED]` and contain only the words actually spoken.

## Eval (stretch)

`scripts/eval_transcript.py` on one transcript:
- Rule checks: all 4 questions asked, in order, at most one follow-up each, feedback present and 2 to 3 sentences.
- LLM judge: was each question actually answered, does each follow-up reference the user's words, is the feedback specific.

- Multiple personas or languages
- Saving users or sessions to a database
- Fallback providers
